### 2.3 Fingerprint algorithms

## 5. What the thread's next step ("group a post's per-file rows by shared name") changes

Nothing of it is written; this is the reading of the plan text against main.

- Trigger: with per-file posters, `split_post_sql`'s `+poster is ?2` (release_info.rs:306) excludes the sibling rows, so `split_post_with` returns `None` for the `.mkv` row and the PAR2 rows alike; each PAR2 volume row is one file with its own subject `[k/9]`, so `union_files` would set `file_total` 9 for all of them and `one_upload`'s `files.len() <= total` test (:342) would pass once the poster predicate is dropped.
- release_info.rs: relax `split_post_sql` (:300-308) to `name = ?1` (poster dropped or made optional), keep the date window (:287-289, :310-314), and let `one_upload` (:339-348) and `linked` (:350-358) decide; probably widen `SPLIT_POST_GROUPS`/the 64-row cap (:220, :306) because a per-file split has one row per file, not per group (a 9-file post is 9 rows in one group). `SplitPost.groups` would then often have one group, so the "N GROUPS" tag (web.rs:777-779) and `listed_id` (:251-253) need a "N ROWS"/lead notion. The name key is `releases.name` (posted name) and the lookup stays on `idx_release_unique(name, group_name)` (store.rs:146): several rows with the same name in the same group are impossible under that unique index, so per-file rows of one post can only exist when ingest gave them different names (random per-file subjects) OR the same name across groups. For the Batman case the thread said the rows share the name and differ in poster; whether the PAR2 rows share the `.mkv`'s release name was not verified from code here (the #46 thread says "the row never reaches the 9 files the post promises", which fits same-name rows blocked by the poster predicate).
- web.rs: the fold at :533-554 and the size override :509-518 call `split_post_with` for incomplete rows only (`if r.complete { return None }` :539-541); per-file rows are each COMPLETE on their own (one file, all parts), so the guard must go or move; `release_page` :1007 has the same `!release.complete` guard; the GROUPS tag :777-779; `copies_html` is unaffected unless the lead row should carry the copies of its members.
- duplicates.rs: `filled_nzb` already goes through `nzb::inventory` (:530), so it inherits any grouping for free. `copies_with`/`counts_with` are keyed by row id, so a grouped post has copies only through the row that holds the fingerprint; and because `covers_all` (archive/steps.rs:240-243) is evaluated per row, a post split per file never gets a `posted` fingerprint, so grouped posts would still show no twins unless Par2Step learns to fingerprint the union (a new writer keyed on the lead row, or a post-level key). That is the duplicates.rs change the thread's checklist implied.
- New tables or columns: none are needed for name grouping (it is read-time, like #46: "nothing stored changes", thread 06:42:59Z). Collision with `segment_crc(file_id, part, crc32, size)` or `par2_files(release_id, seq, name, size, md5, md5_16k, crc32, source)`: none by name (no such tables on main: schema.rs:78-92; nor in #48 `release_cover`, #51 `release_stills`, #64 `upload_link`) and none by key (the grouping keys on `releases.name`, `files.filename`, `files.subject`, `files.seen`; the catalog tables key on `file_id`/`release_id`). ## 8. The re-key precedent: `TWIN_VERSION` bump + `forget_old_twins`

- Mechanism: the twin key carries a version byte (`TWIN_VERSION` = 2, duplicates.rs:92; prefix at :86). At every indexer start (`bg_indexer.rs:1174-1176`) `forget_old_twins` (duplicates.rs:97-117) runs one `begin immediate` batch per shard: rows matching `old` = `(posted is not null and length(posted) != 21) or (posted is null and par2_block is not null)` (:101) are queued in `pp_queue` with `due_at = now` (:104-106), their PAR2 bit is cleared in `pp_state.done`/`failed` (:98, :107-108) and their `posted`/`par2_block`/`par2_blocks` are nulled (:109); a shard without the tables rolls back (:113-115). Par2Step then re-reads the PAR2 first article (archive/steps.rs:216-234, `Needs::Bodies`) and rewrites `SET_POSTED` (:261-264). The second clause catches rows whose old fingerprint was cleared by an earlier deploy but whose sizes remain (:94-96; #34, thread 04:15:31Z "142 old twin fingerprints that would never have been rebuilt"). Tested at tests/duplicates.rs:60-80 ("only the PAR2 step runs again", "and it's queued", "the new form stays", "the old form goes").
- What it costs: a full scan of `release_fingerprint` per shard at each start (the predicate cannot use the partial index), then one body fetch per requeued release under `body_fetches_per_minute` (default 600 per the thread) shared with live indexing: 118M releases would be about 137 days if every one had a key; in practice only rows with a read PAR2 set are touched, and they are re-read newest-due-first through `pp_queue`, not newest-first like a walk.
- Limits to fix before reusing it: (a) detection is by length (21), not by the version byte, so a version 3 of the same length would never be found: change the predicate to `substr(posted, 1, 1) != x'03'` or add a `twin_version` column; (b) the re-read is a body fetch because the inputs (md5s) are not stored; a `par2_files` table would make the next re-key a database-only walk; (c) there is no progress marker (pp_queue rows are consumed), so a half-done re-key is invisible except through `pp_state` bits.
- Compared with the other backfill routes: `Step::config_stamp` (src/postprocess/step.rs:60-62) with `seed_shard` (engine.rs:1073-1114: a new bit queues a `steps` walk newest-first, :1103-1111) re-runs the step for EVERY release; Par2Step defines no `config_stamp` today (steps.rs:192-211), so a stamp would be new there. `atlas --reprocess --step archive_par2 --apply` (reprocess.rs:25-40) is the manual, resumable `pp_walks` variant. `forget_old_twins` is the only targeted, self-triggering re-derivation and the natural model for "rows in release_fingerprint without a par2_files row -> pp_queue".

## 11. Risks

- Perf: `copies_html` and `duplicates_page` are O(copies x articles) per view (§7); any new per-copy fact parsed from `release_probe.info` multiplies by 12 or 60. The Duplicates page's three full `release_fingerprint` scans per view will not survive bodies at scale; a `clusters` count in `meta` or a materialised cluster table is needed before fingerprints cover tens of millions of rows.
- Backfill size: a `par2_files` backfill is one body per release with a PAR2 set (`Needs::Bodies`), bounded by `body_fetches_per_minute` and `bodies_per_release`; at 600/min a 15M-release PAR2 population is about 17 days, 118M about 137 days (docs/port/00-overview.md:7; storage.md §11.4 agrees). Store md5s on the FIRST read from now on so the backfill is only the past. A `segment_crc` fill for every decoded article is probe-fed (storage.md §11.2).
- Schema: additive columns only (`ShardTable.added`, schema.rs:102-110); compaction accepts columns the compacting build knows (storage.md §12.4); an older binary must not compact a newer shard.
- Semantics: twin = whole-posting equality today (web.rs:1570, 1601 hardcode the sentence; README.md:612-614). Per-file proofs change what TWIN means and what `fill_gaps` may borrow (duplicates.rs:479-519 trusts same name + part count + sizes; the #28 Codex finding "gap filling trusts a twin's PAR2 set" was left open by design, thread 02:13:15Z).
- Open PRs touching the same code: #64 edits `release_page`/`release_html` (new last parameter), the `copies_html` call (web.rs:1181 -> conditional), `RowExtras`, `row()` TWIN/ALT suppression, `SplitPost`, `contents_of`'s signature, `nzb::inventory`, ListStep's content writes and SHARD_TABLES:86; #57 rewrites `Search::body` including the Hide copies block (web.rs:533-566) into `fold_split_post`/`body_from_window`; #48 adds `nzb_files_html` right after `release_html` and a `{nzb_files}` slot below `{copies}` (branch hunks at 1141-1188), `probe_html` gains a `cover` parameter, SHARD_TABLES:84; #51/#54 add `release_stills` (SHARD_TABLES:85, StepId(6)) and no web.rs change; the stills strip (#60) adds +54 after `details_html` and hunks at web.rs 61/1110/1139.
