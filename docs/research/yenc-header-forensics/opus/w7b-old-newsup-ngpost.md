# W7B: old NewsUP '@UFK' IDs and the 'Sc5dLs_' / <32hex>@ngPost poster

Sources were cloned read-only (git clone of demanuel/NewsUP, mbruel/ngPost, sanderjo/NZBs, nzbget-ng/nzb-subject). The gh API returned 403 for these repos, but plain `git clone` worked. No third-party code was run. The only script I ran was my own test, t.py in the scratchpad. It is a short mod-4 test and not worth keeping.

## 1. '@UFK' IDs (ubuntu-mate-16.04.2 NZB): the news server assigned them, not NewsUP

- NZB: sanderjo/NZBs `ubuntu-mate-16.04.2-desktop-amd64---Feb2017.iso.nzb`. It has 2582 segments, every one `<32 letters>@UFK`, all unique. poster `NewsUP <NewsUP@somewhere.cbr>`, date 1487587920 (2017-02-20 10:52 UTC), group alt.binaries.test.
- NewsUP commit f37d1a1 (2017-02-20, the same day; HEAD after 02810d0 "Code cleanup" of 2017-02-19), file newsup.pl:
  - :513 `# "Message-ID: <", $segment->{id},">",$CRLF,`: the Message-ID header is commented out, so NewsUP sent no ID.
  - :460-461 and :484-485 `if($read =~ /^240 .*<(.*)>/){ $segmentsIDs{...}->{id}=$1; }`: the ID written to the NZB is the one the server returns in its `240` reply.
  - Window: `git log -S'# "Message-ID: <'` shows this behaviour from 02810d0 (2017-02-19) until 07aa0eb (2017-06-21). 07aa0eb puts the header back (newsup.pl:759) together with the own `"$s$usec.".base36(rand("$s$usec"))."@$time.newsup"` generator (:939-941). Versions before 02810d0 also used the `.newsup` style.
- Conclusion: NewsUP has no '@UFK' generator, so a NewsUP-side RNG cannot be inverted. `[A-Za-z]{32}@UFK` is the posting server's (provider's) own Message-ID format. I did not identify the provider. Guess, unverified: an internal tag of the provider's posting front-end.
- Statistics: 52 symbols, per-symbol counts 1509-1663 (82,624 chars, about uniform). A glibc `rand()%52` lag test (v[31] ≟ v[28]+v[0] mod 4, with carry) gives a uniform spread of 625/687/627/643 for both A-Za-z and a-zA-Z. So the ID is not a simple per-char glibc TYPE_3 stream.
- Linkability: one ID does not predict others as far as tested. The suffix '@UFK' links only to "posted through that provider in 2017", not to the poster. Other NZBs in the repo have no '@UFK'.

## 2. 'Sc5dLs_aLaM5Mn-Ouwr@JxB048gTyZ.qDa' + `<32hex>@ngPost`

- Sample: nzbget-ng/nzb-subject `samples/The.Addams.Family.1964.S00E01...-S1PH3R.nzb`. 36 files, date 1634210923 (2021-10-14). Article size 716800 (the ngPost default, NgPost.h:262 at v4.16). Subject format `[01/36] - "name" yEnc size (1/n)`. meta password `tWJ2LuGKo0XCdRf` (15 chars, A-Za-z0-9).
- Message-IDs: ngPost upstream. NntpArticle.cpp:33/121 `_id(QUuid::createUuid())`, NntpArticle.h:41 `sMsgIdFormat = QUuid::StringFormat::Id128` (32 hex, no dashes or braces), plus the signature `@ngPost` (NgPost.h:264 sDefaultMsgIdSignature). Id128 has been used since v1.2 (2019-11-16, c42c370/444cca2). The samples checked have version nibble 4 and variant b/9: RFC 4122 v4 random UUIDs. Qt5 createUuid takes its randomness from the OS CSPRNG (CoCreateGuid on Windows, QRandomGenerator::system on Unix in Qt >= 5.10; the second is from memory). So the IDs are unpredictable and cannot be linked to each other or to anything else.
- The From was not generated by ngPost. ngPost's randomStdFrom (NgPost.h:598-609 @v4.16) draws `sRandomAlphabet` = `[A-Za-z0-9]` (NgPost.cpp:66) with std::rand and then appends `@ngPost.com`, or `@<msg_id signature>.com` at HEAD. It cannot produce `_` or `-` or a random domain. The same From appears on every file, so it is a fixed `FROM=` in the config (GEN_FROM was off). The shape `[A-Za-z0-9_-]{19}@[..]{10}.[..]{3}` looks base64url-like (e.g. 14 random bytes = 19 chars). Its generator is unknown: a wrapper script or uploader front-end that passes FROM to ngPost. Forks (e.g. Hydro74000) were not checked; there was no time.
- Version and RNG: the post date falls between v4.15 (2021-09-21) and v4.16 (2021-10-29). v4.15+ seeds with `std::srand(QUuid::createUuid().data1)` (NgPost.cpp:315; the old `srand(currentMSecsSinceEpoch)` is commented out at :314). std::rand is used only for randomPass (NgPost.cpp:1155-1162, same 62-symbol alphabet), randomFrom, and random group picks (NgPost.h:531, PostingJob.cpp:739). It is not used for the IDs.
- Linkability: From is a static fingerprint, so exact-string matching links all posts by this uploader. The IDs are CSPRNG and not linkable. The std::rand seed (32 bits on v4.15+, a ms timestamp on <= v4.14) could in principle be recovered from the 15-char password: 2^32 msvcrt LCG on a Windows/MinGW build, or glibc on Linux. Even so, it predicts only other std::rand outputs (group choice, GEN_FROM), not Message-IDs. I did not attempt it; it touches archive-password territory.
