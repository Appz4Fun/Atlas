# w10a: MultiPar / par2j / QuickPar default block-size and recovery-exponent rules

Scope: default slice (block) size, redundancy, first recovery exponent, and GF for MultiPar (par2j CLI and GUI), QuickPar 0.9.1, plus ParPar and par2cmdline for comparison. Status: MultiPar CLI values are quoted from the shipped v1.3.2.9 help. Everything marked UNVERIFIED was not confirmed against source or runtime output.

## Corrections to the brief

- In par2j, `/rf` is the **number of recovery files**, not the first recovery block. The starting recovery block number is `/rs` (Command_par2j.txt: "/rs: Set starting number of recovery blocks ... Default is 0"). So the default first exponent is 0.
- ParPar's `-s0.5w*10` note for MultiPar/par2j: ParPar's arg parser (`bin/parpar.js`) maps the `w` suffix to a "power" unit with `value=0.5, scale=10`. Read literally that is slice = 10 * total^0.5, which matches the par2j `/sr10` rule (see below). The 3000-block cap is not expressed in that ParPar string. UNVERIFIED that ParPar's rounding and cap match par2j.

### Derived par2j default rule (checked against the help table)

With `/sr10`, count/size = 0.01, so block size B satisfies B = 10·sqrt(total) and count N = sqrt(total)/10, then capped at 3,000 blocks (`/sn3000`). Checks against the help table: 600 MB gives 245 KB (B ≈ 245 KB), and 4 GB gives 640 KB (B ≈ 655 KB; table 640 KB). The cap binds above roughly 900 MB, after which B ≈ total/3000. This is a derivation from the docs, UNVERIFIED against the par2j source (not reachable).

## Proves (twin) / Cost (1-few articles)

- **Proves:** Two posts of the same file set made with par2 slice size S and exponent 0 contain the same exponent-0 recovery slice, which is the XOR of all input slices (coefficient 1 for exponent 0). Equal slice size and identical slice boundaries are required. Zero-padding of the last slice must also match.
- **Cost:** Fetch the smallest recovery volume that holds exponent 0 (par2j default `/rs0`, so the first recovery file) and read one or a few articles. Enough to compare against the same slice from a candidate post.

### Which tool pairs can yield identical exponent-0 slices by default

- **par2j (MultiPar CLI default) with par2j default:** Yes, for the same total size (same B from the sqrt rule). Both produce exponent 0.
- **par2j with ParPar `-s0.5w*10`:** Likely identical B by design (UNVERIFIED rounding and cap). Mismatch is possible for totals above about 900 MB, where par2j's 3,000 cap applies.
- **par2cmdline default with ParPar `-s2000`:** Yes, same B (ceil(total/2000) rounded to multiple of 4). Verified earlier for par2cmdline.
- **par2j with par2cmdline:** Not by default. For total 4 GB, par2cmdline B ≈ 2.1 MB while par2j B ≈ 640 KB. Different slices.
- **QuickPar with anything:** Cannot be determined. QuickPar defaults are UNVERIFIED.

## 5 bullet takeaways

- par2j's `/rf` is the file count. Starting exponent is `/rs`, default 0. A MultiPar set therefore includes exponent 0 by default, so the XOR-slice fingerprint is available whenever recovery is created.
- par2j with no slice options uses `/sr10 /sn3000`. Block size is about 10·sqrt(total), capped at 3,000 blocks. This is the single most useful default to match for twin detection (UNVERIFIED against source).
- par2j and par2cmdline defaults differ for typical Usenet sizes (600 MB to 4 GB). Only a pair with the same rule will yield identical exponent-0 slices. Using MultiPar against a par2cmdline post is a non-match by default.
- ParPar's `-s0.5w*10` note matches the par2j rule numerically, so ParPar set to that value is the likely fingerprint-compatible generator (UNVERIFIED).
- GF(2^16) with 0x1100B for MultiPar is only suggestive from the binary constant scan (UNVERIFIED). A runtime cross-check with par2cmdline `verify` on a MultiPar-made set is still needed to confirm byte compatibility.
