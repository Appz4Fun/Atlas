## Syntax confirmed

- Keywords (srrdb.com/help, says they "also work in the api"): `r:`, `group:`, `date:`, `nfo:`, `srs:`, `foreign:`, `confirmed:`, `rarhash:`, `category:`, `imdb:`, `start:`, `genre:`, `language:`, `country:`, `archive-crc:` (example `archive-crc:3D7C3182`), `archive-size:`, `isdbhash:`, `lower:yes`, `firstupper:yes`, `compressed:`, `skip:`, `skipr:`, `store-real-filename:`, `store-real-crc:`.
- Combined search: keywords are path segments joined with `/` (AQTKU `search/${keywords.join('/')}`; WarezBot `search/<x>/order:date-desc/skip:5`). Clients pass `archive-crc:<crc>/archive-size:<n>` together, so a combined query is supported in practice.
- Ordering: `order:date-desc` is used by SickGear and WarezBot; the toolkit lists four order values.
- CRC case: nzbfast sends uppercase 8-digit hex; details CRCs are compared lowercased by xbmc namefix.
- Host: current clients use `https://api.srrdb.com/v1/...`; older ones use `www.srrdb.com/api/...`. Prefer `api.srrdb.com/v1`.
- Details: `/details/<release>` (URL-encoded), fields `archived-files[]` with `name`, `size`, `crc`. Some code reads `files[]` as well (xbmc namefix), so handle both.

## Response shapes (from client parsers)

- Search: `{"results":[{"release":..., "date":..., "hasNFO":"yes|no", "hasSRS":..., "isForeign":..., "imdbId":..., "size":...}], "resultsCount": 1, "warnings": [], "query": [...]}`. `resultsCount` is a number in the live API but was seen as a string (scryer, rescepy compares to `'1'`). Treat both as valid.
- Miss: `results: []`, `resultsCount: 0`.
- Collision: two or more results. nzbfast refuses to pick one. Only a single row counts as identification.
- Details: unknown release returns 404; malformed name returns 400 (scryer and xbmc both treat these as cache-worthy misses).

## Rate limit and etiquette

- srrDB's terms (as quoted in code comments, not fetched from the site): "asks callers to use the API rather than scrape it"; "asks to be used but not scraped"; refuses connections when hit too quickly.
- Clients do about 1 request per second per host (AQTKU PQueue 1/s, scryer 1 rps, xbmc min-interval).
- Retry: on 429 or 5xx, back off (xbmc 30 s x attempt; nzbfast honors Retry-After). scryer and nzbfast do not retry on transport failure.
- Caching: nzbfast caches by CRC for the process lifetime, including misses. xbmc caches JSON on disk. pySceneTools caches in SQLite.
- Size 0 is never queried (it matches everything).
- Auth: none in any client.
- srrdb.com/help mentions logging in "could make you see more options". Not confirmed for the API.

## Recommended Atlas lookup (UNVERIFIED)

Use the inner-file CRC32 from the last RAR volume header (or the first volume's file header if the set is not header-encrypted) as the query: `GET https://api.srrdb.com/v1/search/archive-crc:<CRC8HEX>`. Accept only when `resultsCount` is 1 and `results[0].release` is present. Use a payload file size only as a second key (`archive-size:<bytes>` combined with `archive-crc:`) to reject a CRC collision. Treat a single hit as an alt or twin of the scene original, not proof of identity beyond its CRC plus size. Cost: 1 article fetch (already needed for the header) plus 1 API call. Cache the result per CRC and per release for the process lifetime, and cache misses too. Skip header-encrypted (`-hp`) sets, which expose no inner CRC. Keep to about 1 request per second and do not retry on error.

## Takeaways

1. Use `https://api.srrdb.com/v1/search/archive-crc:<8-digit upper hex>`. Older `www.srrdb.com/api/...` paths still appear in client code.
2. Accept a result only when it is exactly one row. Multiple rows are a CRC collision, and clients refuse to pick one.
3. Combine keys as path segments: `archive-crc:<hex>/archive-size:<n>`.
4. Pace to about 1 request per second, honor Retry-After or back off 30 s on 429/5xx, cache hits and misses, and never retry in a loop.
5. Details (`/v1/details/<release>`) gives `archived-files[].{name,size,crc}` for confirmed releases. Parse both `files` and `archived-files`.
